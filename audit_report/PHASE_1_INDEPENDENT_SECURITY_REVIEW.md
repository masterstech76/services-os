## 3. Unresolved Vulnerabilities Identified in This Review

1. **Direct `ADMIN` Table Access to `user_mfa_credentials` (Requirement 3 — `FAIL`):**
   - `CREATE POLICY "Admins inspect MFA credentials" ON user_mfa_credentials FOR ALL TO authenticated USING (public.is_admin()) WITH CHECK (public.is_admin());` exposes all users' `totp_secret_encrypted` and `recovery_code_hashes` to any authenticated `ADMIN` via PostgREST and permits direct `UPDATE`/`DELETE` bypassing lockout and anti-replay controls.
   - **Required Fix:** Drop `"Admins inspect MFA credentials"` on `user_mfa_credentials` so `authenticated`/`anon` have **zero** direct table access (`service_role` + `SECURITY DEFINER` RPCs only).
2. **Missing Server-Side MFA Session Enforcement on Protected API/RLS Operations (Requirement 4 — `FAIL`):**
   - Protected table RLS policies (`bookings`, `payments`, `users`, `tenants`, `audit_logs`, etc.) and `is_admin()` / `is_staff()` do not verify that the caller's session has completed MFA (e.g., Supabase native MFA `auth.jwt() ->> 'aal' = 'aal2'`, or an equivalent server-verified MFA session check).
   - **Required Fix:** Enforce server-side MFA verification (e.g., Supabase Auth MFA `aal2` or server-bound MFA session claim) inside `is_admin()` / `is_staff()` or protected RLS/RPC gates before accepting Phase 1 as production-hardened.
